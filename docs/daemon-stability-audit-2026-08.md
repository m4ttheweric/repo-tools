# rt daemon stability audit and hardening roadmap

**Date:** 2026-08-27 · **Scope:** the daemon process (`lib/daemon.ts`, `lib/daemon/**`, `lib/state/**`, transitive imports, launchd/tray supervision) · **Trigger:** the daemon has grown from a personal convenience process into the backbone of an app about to be shared with other people.

## Method

Eleven parallel audit lenses (lifecycle, transport, state, background work, worktree engine, chat/agent/events, integrations, architecture rot, observability, concurrency sweep, share-readiness) each read their subsystem in full. 210 raw findings deduplicated to 169: 108 bug/hazard plus 61 structural, of which three were same-document duplicates folded into one entry in Appendix B, leaving the 58 listed there. Every bug/hazard finding (108) was independently re-verified by an adversarial "try to refute this" agent that re-read the code (Opus 4.8 for P0/P1, Sonnet for P2/P3); several verdicts rest on empirical probes run in isolation (Bun busy-code behavior, runCapture grandchild survival, unhandledRejection delivery on the prod entry path). Structural rot/gap findings (58 after dedup) were adjudicated by the lead reviewer from finder evidence. Verdicts: **104 confirmed, 4 refuted**. Refuted claims are listed in Appendix C so they are not re-raised.

Severity legend: **P0** active crash/data-loss with user impact · **P1** reliability failure or silent feature drop under realistic use · **P2** latent, bites under specific conditions · **P3** quality/operability.

## Field evidence (from ~/.mattstack/rt/logs, 2026-07-30 through 2026-08-28)

The audit's central claims are not hypothetical; the daemon's own logs show the classes in the wild:

- **A real crash loop, invisible end to end.** 2026-08-25 14:01-14:04Z: 24 consecutive fatal `Failed to start server. Is port 9401 in use?` boots, ~10s apart under launchd KeepAlive. Each iteration unlinked and re-bound `rt.sock` before dying, stealing the socket from the 9401 holder. No surface (tray, status, notification) reported it (S043, R001, R002).
- **Event-loop stalls, mostly but not fully fixed.** 900+ command handlings over 15s in late July and on 08-06 (the async-scanner fix landed mid-window); 8 residual since 08-13. `system-processes` p99 is 6.1s over 293k calls, max 76s. The remaining sync-exec sites in Phase 1 are the same class (S008, S015, S045).
- **The boot path runs many times a day by design.** 5-14 daemon boots/day in the last week; 196 of 217 exits were clean signal exits from deliberate dev-cycle restarts, which is normal workflow here and not itself a problem. The relevance is exposure: a boot path exercised this often must fail loudly when it does fail.
- **Contract noise.** `command rejected` is dominated by `events:head` (287), `project-mrs:read` (183), `runs:list` (131): clients drifting against untyped payloads (R013).
- Zero `unhandledRejection` lines in 30 days of logs, which corroborates that the swallow path (S001) hides failures rather than logging them.

## Executive assessment

The daemon's core seams are genuinely good: one command seam that logs every outcome, factory-built handlers over a shared context, a write-through SQLite store with a stated contention policy, a park gate that keeps a wrong-flavor daemon inert, and a worktree engine whose destructive steps are guarded by registry-first design, per-tree locks, and rename-to-trash. The unit-test base (43 daemon test files) is real. This is a better-than-typical codebase for its age.

The instability lives in four places, and they are consistent:

1. **The supervision contract is fiction on the shipped path.** The crash policy was designed for `bun run lib/daemon.ts` (a throw exits 1, launchd restarts). The prod binary boots through `cli.ts`, where a `startDaemon()` throw is delivered to the `unhandledRejection` listener and the process lives on as a zombie that every surface reports as healthy (S001, P0). Failures earlier than that crash-loop with no log line anywhere, because stderr redirection and crash handlers install mid-boot (S003, S004). There is no restart counter, no last-crash reason, no stall detection, no degraded state (R001-R003, R011). A daemon this central must fail loudly and visibly; today it fails silently in both directions.
2. **The event loop still gets blocked.** The "never execSync on the daemon thread" rule exists because it already caused a wedge (MAT-222) and a tray-flicker incident, but it is enforced by memory, not by a gate. Five sync git spawns per repo still run inside every 5-minute refresh, disposal runs a system-wide sync `lsof`, and `runCapture`'s timeout is defeated by any grandchild that holds the pipe, which can retire the worktree reconciler for the daemon's lifetime (S008, S015, S023/S024). One bug (S011) quietly gives the daemon a 5000ms `busy_timeout`, so the SQLITE_BUSY policy the whole state layer was written against has never actually engaged in production.
3. **The trust boundary on 127.0.0.1 assumes the author's machine.** The WebSocket broadcast has no origin or token check, so any web page in any browser can watch MR bodies, repo paths, and process argv scroll by (S005/S006); several mutating routes skip the token (S040, S041). Fine for one developer who wrote it; not fine for someone who installs mattstack.app and browses the web.
4. **Rot is concentrated, not diffuse.** Fourteen side effects arm at module import; every new subsystem edits daemon.ts in three places because there is no lifecycle seam; 48 of 91 commands are untyped `any` contracts; ordering constraints live in comments; and the previous audit doc (docs/daemon-runner-health.md) describes a subsystem deleted months ago. None of this crashes anything today. All of it raises the probability that the next ten changes do.

The roadmap below is ordered so that visibility lands first (you cannot stabilize what you cannot see), the stall class dies second and stays dead via a gate, the boundary tightens third, and only then does judgment-heavy surgery on the destructive engine and the module structure proceed, with the new observability as the safety net. Portability work (someone else's Mac) closes it out, though a few of its items gate sharing regardless of order.

## Roadmap

Phases are ordered by leverage, smallest and most urgent first. Each item lists the findings it retires, a size, and the superpowers execution mode: **SDD** means the item is specified well enough by this document plus the finding's fixer notes to go straight to `superpowers:subagent-driven-development` (test-first); **B/S/P** means it needs `superpowers:brainstorming` then a spec and plan first, because there are real design decisions. One phase = one lane/branch; items within a phase are commit-sized tasks.

Already-tracked overlaps: RT-56 (home-snapshot push silently suppressed), RT-51 (recoverable disposal), RT-52 (.worktrees location), RT-73 (shim PATH), RT-64 (dev-mode verify false criticals; folds into 0.5's status-verdict work), RT-74 (run reopen; a runs feature defect outside this audit's scope, deliberately deferred). Where a phase touches one, fold the ticket into the lane rather than duplicating it.

### Phase 0 · Honest supervision: crashes become visible and recoverable

The highest-leverage work in the audit. Everything else assumes you can tell when the daemon is broken. Size: one SDD lane, ~10 commit-sized tasks. Mode: **SDD**; make task one a half-page sketch of the status-verdict set and exit-code semantics, since 0.5 and 0.6 carry the lane's design content.

- **0.1 Fatal means exit.** Make every boot failure on the prod path exit non-zero: wrap the boot sequence so a `startDaemon()` throw is fatal (log + exit 1) instead of feeding the `unhandledRejection` swallow; document the policy split (boot throws are fatal, steady-state rejections log and continue). Retires S001 (P0), S037. Trivial diff, highest payoff.
- **0.2 Crash handlers first.** Move `redirectNativeStderr()` + `installCrashHandlers()` above every module-scope side effect in `lib/daemon.ts` (before the legacy-dir migration and the park loop), so pre-boot failures land in the crash log instead of a discarded stderr. Retires S003, S004, R007.
- **0.3 Bounded boot-failure behavior per class.** EADDRINUSE on 9401: do not bind `rt.sock` before the API bind succeeds (the 08-25 loop stole the socket 24 times); log the holder (lsof) and park-retry with backoff instead of crash-looping; honor an `rt.apiPort` setting as the escape hatch (RT-45 precedent: RT_API_PORT exists). state.db open/migrate failure: bounded backoff plus a quarantine marker surfaced by `rt daemon status`. Retires S043, S037, S074 (importer wrapped per-store).
- **0.4 events.db joins the discipline.** Open it inside `startDaemon()` after crash handlers, with busy_timeout, synchronous pragma, and the same corruption quarantine state.db has; guard the sweep timers. Retires S009, S035.
- **0.5 Restart and crash visibility.** Persist a restart counter and last-exit reason (kv table); `rt daemon status` and `/api/status` gain verdicts for `boot-failed`, `crash-looping`, `alive-but-not-serving`, `parked`; the tray dot maps them (fixes the eternal yellow, S026). Rotate/prune `daemon-stderr.log` and `tray-crash.log` and stamp entries so stale content is never shown as current (S029). Retires R001, R002, S026, S029.
- **0.6 start/stop honesty.** `rt daemon start` kickstarts a registered-but-stopped agent instead of register-only; `shutdown`'s exit-0-stays-down semantics get documented and paired with a working `start`; uninstall refuses to unlink `rt.sock`/`rt.pid` while a live pid holds them; eviction and cleanup check file ownership (pid stamped in the file) before unlinking. Retires S028, S036, S060, S027, S030, S012, S044.
- **0.7 Two one-line correctness fixes that gate everything above.** `startHomeSnapshot` opens state.db daemon-flavored (S011); `isBusyError` matches the extended busy codes and read-then-write daemon transactions use `BEGIN IMMEDIATE` (S072, S073). These make the contention policy real for the first time.
- **0.8 Retire the stale audit doc.** Replace `docs/daemon-runner-health.md` with a pointer to this document (R017, R058 comment sweep rides along).

### Phase 1 · The event loop is sacred, and a gate keeps it that way

Kills the wedge/stall class that produced MAT-222, the tray flicker, and the 76s handler tail. Size: one SDD lane. Mode: **SDD**.

- **1.1 Excise sync exec from daemon-reachable code.** Replace `execSync`/`sleepSync` with `runCapture`/`git-async` in: cache-refresh branch listing and remote-url (S008, S045), `git-worktrees.ts` callers on the daemon tick and `repos` verb (S021), freshness `getRemoteUrl` (R032), `/api/repos` worktree listing (S055), worktree-process-kill's lsof/ps trio (S015, S016), repo-index identity resolution reached by `endpoint:claim` (S098), boot-reconcile's `sleepSync` (S044 rides 0.6).
- **1.2 runCapture that actually times out.** Spawn children in their own process group, escalate SIGTERM to SIGKILL on deadline, and bound the post-kill stream drain, so a pipe-holding grandchild cannot hold the promise open. This one fix also un-wedges the reconciler's stuck-ready-step failure mode. Retires S023, S024; revisit S104's shared 60s mutating-verb timeout while in the file.
- **1.3 The gate.** A test in the spirit of `no-eager-tui.test.ts`: walk the daemon's import graph and fail if any daemon-reachable module imports `execSync`/`spawnSync`/`Bun.spawnSync`/`sleepSync` (allowlist for boot-only `user-path.ts` until Phase 6 replaces it). The rule has been re-broken twice; only a gate keeps it dead.
- **1.4 Refresh cannot wedge.** Per-repo deadline plus a whole-cycle deadline on the coalesced refresh promise so one hung GitLab call cannot pin `refreshInFlight` forever (S007); provider cache drops entries when `gitlabToken` changes (S048, S049).
- **1.5 Scan cost sanity.** Skip the 10s system-process scan and 30s port scan when no consumer has asked recently (tray connected, recent CLI call); single failed lsof no longer resets runaway windows (S058, S093, S061, S038/S039/S101 fold in: batch or cache run-DB opens).

### Phase 2 · Health you can see

Small spec first (one page: the health model), then SDD. Retires the observability gap cluster.

- **2.1 A degraded state.** `tray:status`/`/api/status` report degraded when refreshes fail consecutively, with the failing subsystem named (R011); memory/handle/uptime metrics included (R012).
- **2.2 Stall detection.** A self-heartbeat (timer writes a monotonic stamp; status compares) so a blocked event loop is distinguishable from "not running" on every surface (R003).
- **2.3 Log ergonomics.** `rt.logLevel` setting read at boot and on change (R004); cap daily log growth with warn-storm suppression (S031); pino stream gets an error listener so a full disk cannot turn every log call into a throw (S032); resolver console.warn noise demoted (S033, R005).
- **2.4 Request attribution.** A request id plus caller tag (cli/tray/board pid) on every command, logged at the seam, echoed in `ok:false` envelopes (R008); unknown-command replies distinguish version skew via the ping version (R021).

### Phase 3 · The 127.0.0.1 trust boundary

The daemon must assume a hostile browser on the same machine. Size: one SDD lane. Mode: **SDD** (policy decisions are small and named here).

- **3.1 WS auth.** Token (query param or first-message auth) plus Origin allowlist on `/ws`; broadcast send failures counted and dead clients dropped (S005, S006, S042).
- **3.2 Token-gate the strays.** `POST /api/hooks/:repo/repair`, `POST /api/refresh`, and the destructive `GET /api/notifications` drain join the token gate; hooks:repair keeps working from the unix socket untokened (S040, S041, S084).
- **3.3 One token read.** Single loader with mtime re-read shared by api-server and secrets handler (S054).
- **3.4 Input hygiene.** `maxRequestBodySize` on both servers (S092); reject `--`-prefixed branch/ref args before they reach git argv (S010); coerce REST GET query params per catalog types so documented flags work (S085; the path-param decode 500s are S083, owned by the cross-cutting list); redact credential-bearing remote URLs in logs and errors (S050).

### Phase 4 · The destructive engine earns its paranoia

The worktree engine's guards protect against rt's own recorded state but not against the process table, the filesystem, or a dropped db write. These are judgment calls, not mechanical fixes. Mode: **B/S/P** (brainstorm the policy, spec, then SDD). Fold in RT-51 and RT-52; RT-34's pool history is context.

- **4.1 Process-kill correctness.** cwd-prefix matching with the pool root inside the main clone means `autoReturnMain` can kill every sibling tree's dev server, and the blocklist approach SIGTERMs editors, tmux, and the calling CLI. Decide: match on exact tree root, allowlist what rt itself started (endpoint claims know), never kill on the main clone path. Retires S017, S018, and the S015/S016 sync-lsof interplay (mechanics moved by 1.1).
- **4.2 Stash discipline in freshen.** Never pop a stash the current pass did not verifiably push (stamp the stash message, verify before pop); reconsider stash-in-live-checkout entirely for idle-main freshen (S019, S064).
- **4.3 Registry writes are critical.** Worktree registry and claim-state writes use the critical-write path (retry, then refuse the destructive action) instead of warn-and-drop persistOrWarn (S025); dispose re-reads the record under the lock (R040); reconcile treats a missing path as "hold and re-verify next pass" rather than prune (S063).
- **4.4 Trash and reap guards.** `.trash` never materializes inside the user's repo unless the exclude is in place (S078); the reaper only touches directories whose name matches rt's own epoch stamp format and provenance (S079); disposal recoverability lands here (RT-51).
- **4.5 Claims and adoption.** Endpoint claim liveness records boot-id alongside pid so reboot pid-reuse cannot pin ports (S068); `worktree adopt` requires explicit opt-in to auto-dispose semantics (S056); team-declared on-deck pools default off on machines that never opted in (S077).

### Phase 5 · Structure that stops the rot

The architectural phase. Mode: **B/S/P**, executed as two or three lanes; high blast radius, so it goes after observability exists to catch regressions.

- **5.1 A lifecycle seam.** Replace the fourteen module-scope side effects with an ordered boot list of units, each `{name, start(), stop()}`, constructed inside `startDaemon()`; cleanup derives from the same list; the three copy-pasted sweep timers become one helper with per-sweep config; `emit()`'s per-event business logic moves behind a subscriber registration. Retires R006, R009, R019, R020; unlocks in-process lifecycle tests (R031) and closing state.db at shutdown (R022).
- **5.2 Contracts all the way.** The remaining 48 untyped commands (everything the Swift tray calls, plus `cache:read`) join the rt-client catalog with payload validation at the seam (reject with a typed error instead of handler-throw); handler error envelopes converge on one shape (R013, R016, R010, R033, R034, S085's coercion generalizes, R035).
- **5.3 One owner per concept.** Single `RepoIndex` declaration; `repoName`-is-identity encoded in a type alias rather than five comments; canon/patchTree/numericUserId/TERMINAL deduped to one module each (R037, R039, R029, R028, R038 trimmed HandlerContext).
- **5.4 The daemon graph sheds the CLI.** Break the `notifier -> repo-arg -> fzf/ink` import chain (R050) so the daemon bundle stops carrying the TUI; extend `no-eager-tui` to assert it.
- **5.5 State growth and scan bounds.** Retention for `chat_messages` and `agents`; events journal queries take a LIMIT and push the topic glob into SQL; waiter cursors advance (R053, R054, S047, R030, S102); a `state.db` integrity check plus periodic backup answers R055; document the SCHEMA_VERSION claim protocol next to the constant and make column adds self-healing outside the version gate (R015, R056).
- **5.6 Seam tests.** Integration tests for socket-server and api-server (routing, token gate, WS upgrade, 500 envelope, CORS), eviction/shutdown file ownership, pollers wiring, and the boot-order invariants that comments currently carry (R024, R026, R027, R047, R018, R023).
- **5.7 Reconciler decomposition.** Split worktree-reconciler.ts's five duties (reconcile, reactor, freshen, replenish, shrink) into units behind the 5.1 seam; queue kicks instead of dropping them (R014, S065, S094, R041, R049). This is the largest single item and can trail the rest.

#### S001 · P0 · hazard · `cli.ts:184`
**Prod daemon becomes a live zombie when startDaemon() throws: launchd, tray and CLI all see it as up**

Verified on Bun 1.3.13 (scratch script, no rt involved): with an unhandledRejection listener registered, `__main().catch((err) => { throw err; })` is delivered to the listener and the process keeps running (exit never happens; a later setTimeout fires). In the compiled prod daemon (`Contents/MacOS/rt --daemon`), `startDaemon()` installs that listener at line 392 and then can throw synchronously at several sites: `startApiServer` -> `Bun.serve({port: 9401})` throws EADDRINUSE synchronously (verified) whenever the previous daemon has not released 9401 within evictStaleDaemon's 300ms (it is often mid-`execSync` in cache-refresh.ts:119) or another local app holds 9401 (API_PORT is hardcoded, daemon-config.ts:72); `openBranchCacheStore()` -> `runMigrations` throws SQLITE_BUSY after the 5s budget while a CLI holds the write lock, or throws on a disk-full/partially corrupt db. Result: rt.pid already written (line 416), one `unhandledRejection` error line in the log, and a process that stays alive with only the module-scope timers running: no socket (or a socket that the still-exiting old daemon then unlinks), no API, no signal handlers, no pollers. launchd sees a healthy pid and never restarts it; the tray goes red 'Daemon: not running'; `daemonQuery`'s auto-restart and `rt daemon start` only call SMAppService.register (a no-op when already registered) and print 'daemon starting… check logs' forever. Only `rt daemon restart` (kickstart -k) recovers. In source mode (`bun run lib/daemon.ts`) the same throw is a top-level exception and exits 1 (also verified), so the author's dev machine never sees this; every other user's machine runs the prod path.

*Fix (small):* Make boot failure fatal on both entry paths: wrap the body of `startDaemon()` in try/catch that logs `fatal` and `process.exit(1)` (launchd then restarts, and the failure is visible), or have cli.ts call `startDaemon()` inside its own try/catch with the same exit. Independently, write rt.pid only after both servers are bound, and consider a boot-phase flag so `unhandledRejection` exits 1 until `daemon ready` is logged. Add a test that spawns the compiled entry with RT_API_PORT already bound and asserts a non-zero exit.
*Fixer notes:* Root cause is that installCrashHandlers' unhandledRejection handler (lib/daemon-logger.ts:242-244) treats a BOOT-time throw identically to a recoverable runtime stray rejection. Do NOT simply add process.exit(1) to that handler unconditionally: that defeats its intended runtime-recovery purpose. Instead either (a) wrap the body of startDaemon() (lib/daemon.ts:385-514) in try/catch that logs fatal and process.exit(1), or (b) gate the handler on a boot-phase flag so it exits(1) until "daemon ready" is logged (lib/daemon.ts:513). Independently, move the rt.pid write (lib/daemon.ts:416) to AFTER both server binds (after line 469) so a failed boot never leaves a live-pid file. IMPORTANT blast-radius: exiting on boot failure turns the silent zombie into a launchd crash-loop when the trigger persists (e.g., another app permanently on hardcoded 9401 at lib/daemon-config.ts:72, or a wedged write lock) -- so pair the exit fix with (i) a bounded bind retry / port fallback for API_PORT and (ii) replacing evictStaleDaemon's fixed 300ms (lib/daemon/boot-reconcile.ts:24) with actual verification that port 9401 is released before binding; a bounded crash-loop that launchd surfaces is still strictly better than a silent unrecoverable zombie. Tests to add: spawn the compiled --daemon entry with a listener already bound on RT_API_PORT and assert non-zero exit + no stale live rt.pid; and a SQLITE_BUSY test holding the state.db write lock >5s across daemon boot asserting the same. Also note cache-refresh.ts's synchronous execSync git calls on the daemon thread are the reason evictStaleDaemon's SIGTERM is not honored in time -- that is a separate but contributing hazard.
*Partial mitigation today:* Partial only. evictStaleDaemon (lib/daemon/boot-reconcile.ts:16-26) reduces the same-flavor EADDRINUSE-on-restart window but is a fixed 300ms sleep with no port-release verification, so a slow-to-die old daemon (mid-execSync) still wins the port. openStateDb's corruption quarantine (lib/state/db.ts:489-494) covers only the corrupt-db sub-case of throw site A (SQLITE_CORRUPT/SQLITE_NOTADB surfaced by the early PRAGMA user_version probe at line 488); it does NOT cover SQLITE_BUSY, SQLITE_FULL, or corruption that first manifests mid-migration. parkUntilIntended (lib/daemon.ts:103) prevents only the wrong-FLAVOR collision, not same-flavor port contention or a third-party app on 9401. None of these prevent the swallow-and-zombie once a throw does propagate.

#### S002 · P1 · bug · `lib/agent-herdr.ts:28`
**rt agent hardcodes ~/.local/bin/herdr while setup installs herdr via brew**

A teammate with Homebrew clicks Install on the herdr row; `brew install herdr` places the binary at /opt/homebrew/bin/herdr and the tool.herdr row goes green. Later `rt agent start` (surface herdr, the default per handlers/agent.ts:132) runs runCapture(['/Users/x/.local/bin/herdr','workspace','list']); Bun.spawn throws ENOENT, runCapture returns exitCode -1, and the user sees 'herdr workspace list failed (-1): ' with no hint that the path is wrong. The same default is used by herdrAgentWait. Only the author's vendor-script install (which drops herdr in ~/.local/bin) works.

*Fix (trivial):* Resolve like lib/cswap.ts does: `process.env.HERDR_BIN ?? Bun.which('herdr') ?? join(home,'.local','bin','herdr')`, and surface ENOENT as 'herdr not found' with the setup remedy.
*Fixer notes:* Fix at lib/agent-herdr.ts:28 mirroring lib/cswap.ts:28-30: `const bin = process.env.HERDR_BIN ?? Bun.which("herdr") ?? join(home, ".local", "bin", "herdr");`. Bun.which reads process.env.PATH at call time (not Bun.spawn's start-env resolution), and the daemon overlays the user's full login PATH onto process.env.PATH at boot (lib/daemon.ts:120-122, resolveUserPath), so Bun.which("herdr") resolves /opt/homebrew/bin/herdr inside the daemon ... this exact pattern already works for cswapBin() in the same process, so the fix is proven in-context and strictly better (the ~/.local/bin fallback preserves current behavior if resolveUserPath ever returns null). Also surface ENOENT distinctly: when the resolved bin does not exist, throw a "herdr not found (install via `rt setup` / brew) " message instead of the bare "failed (-1)". Add a regression test alongside lib/__tests__/agent-herdr.test.ts that asserts defaultHerdrRunner prefers a PATH-resolved herdr over the ~/.local/bin fallback. Blast radius: agent:start/agent:resume (handlers/agent.ts:93) and rebase-escalation.ts:211 both consume defaultHerdrRunner, so both are fixed by the one change; herdrAgentWait shares it too.

#### S003 · P1 · hazard · `lib/daemon.ts:85`

#### R001 · P1 · gap · `commands/daemon.ts:325`
**rt daemon status cannot say 'process alive but not serving' (parked, boot-blocked, wedged)**

The daemon is parked (wrong flavor), blocked in state.db open behind a CLI import, or stuck in `$SHELL -ilc` because a user's .zshrc waits on a prompt. rt daemon status says 'installed but not running / run: rt daemon start'; start POSTs /daemon/start to the tray (already registered), waits 3s, prints 'daemon starting… check logs'. The user repeats this indefinitely. Nothing on the CLI surface says a process is alive and where it is stuck; the only trace is an info line in a log they cannot read.

*Fix (small):* Extend DaemonStatusVerdict with `alive-not-serving`: when ping fails but kill(pid,0) succeeds for rt.pid OR `pgrep -f 'rt --daemon|lib/daemon.ts'` finds one, print 'process  is running but not answering rt.sock (booting, parked, or wedged) ... rt daemon logs -t'. Have the daemon write a boot-phase breadcrumb (finding 1) so the verdict can name the phase. Add a test for the new verdict in lib/__tests__/daemon-status.test.ts.

#### R002 · P1 · gap · `lib/daemon-logger.ts:237`
**No restart counter or last-crash reason on any surface; a flapping daemon looks healthy between crashes**

A handler throws synchronously on every 5-minute refresh (e.g. a bad settings value in doppler-sync). Daemon dies, launchd restarts it in 10s, it runs 5 minutes, dies again: 12 restarts/hour. Tray is green 95% of the time with a brief red blink; board/console websocket clients reconnect silently; rt daemon status shows 'running, uptime 3m' and nothing else. Nobody is told the daemon has restarted 200 times today or what the fatal line said; the fatal is buried in a 14-day JSON log the user cannot open without lnav/logdy.

*Fix (medium):* Persist a boot-failure record (reason, count, timestamp) under rtDir() from the fatal path; have startDaemon back off (park) after N consecutive failures within M minutes instead of exiting; surface the record in `rt daemon status` and `rt verify`.

#### R003 · P1 · gap · `lib/daemon/handlers/status.ts:23`
**No event-loop stall detection; a wedged daemon is reported as 'not running' by every surface**

A refresh over a large repo runs `git for-each-ref` via execSync on an NFS/slow volume, or lsof hangs during a worktree return. The loop stalls 5-60s. Tray: two 2s timeouts -> red 'Daemon: not running' while the pid is alive; the panel's Restart kills a daemon that would have recovered. rt daemon status: if ping squeezes through, 'likely mid-sync' (a guess with nothing behind it); if not, 'not running'. The daemon logs nothing about the stall before, during, or after. The memory notes show the author diagnosing exactly this with a hand-rolled curl latency loop; a user cannot.

*Fix (medium):* Add lib/daemon/loop-monitor.ts: setInterval(100ms) measuring drift; keep {lagMs, maxLagMs, stalls, lastStallAt, lastStallCmd}; log warn when drift > 1s with the command in flight (track current cmd in handleCommand). Expose `eventLoop` in ping/status/tray:status. Tray: when the pid from the last good status is alive (kill 0 via the socket owner or rt.pid) but polls time out, show 'unresponsive (pid N)' orange, not 'not running'. rt daemon status: print maxLag and last stall on the degraded branch instead of 'likely mid-sync'.

#### R004 · P2 · gap · `lib/daemon-logger.ts:102`
**Log level is only settable via RT_LOG_LEVEL, which launchd/SMAppService never provides; command traces are debug-only**

A user reports 'the board goes stale'. Support asks for debug logs. There is no way to raise the level of the launchd-spawned prod daemon without editing the plist inside the signed app bundle (which breaks the signature and Login Items). At the default level, the log contains no record of successful commands or their durations, so a 30s mr:action or a 240s events:wait leaves no trace; only rejections/throws are visible.

*Fix (small):* Read `rt.logLevel` (machine scope, registered per docs/settings-architecture.md) at boot with RT_LOG_LEVEL as override; add a `daemon:log-level` IPC + `rt daemon log-level ` that sets logger.level live and logs the change; additionally log successful commands at info when durationMs exceeds a threshold (e.g. 2s) so latency outliers are visible at the default level.

#### R005 · P2 · gap · `lib/daemon-logger.ts:249`
**All stderr writes become level=error and unhandled rejections are swallowed uncounted, polluting error filters**

Bun runtime deprecation notices, library console.error chatter, and `git` stderr forwarded by a dependency all land as level=error. A user (or the tray's future health computation) filtering on error sees dozens of benign lines per hour and misses the real one. Meanwhile a code path that rejects on every tick (a broken poller) is logged at error and otherwise invisible: no counter reaches status, so a daemon that is functionally dead in one subsystem keeps reporting healthy.

*Fix (trivial):* Map intercepted stderr to warn with source:'stderr' (error only when the text starts with a known panic/exception prefix). Count unhandledRejection and uncaught-but-recovered errors in a process-wide counter exposed in status/health (finding 10).

#### R006 · P2 · rot · `lib/daemon.ts:78`
**lib/daemon.ts arms fourteen live side effects at import; startDaemon() is not the entry point**

Any `import "./lib/daemon.ts"` (a future unit test, a tool, a mis-wired command module, the module registry) starts timers, opens events.db and state.db, spawns git against ~/.mattstack/user, and runs a login shell, before startDaemon() is ever called. The park gate had to be placed 'above every subsystem' precisely because construction is import. Every new subsystem the next ten changes add lands here with the same trap, and the ordering constraints exist only as 14 comment blocks (lines 41, 74, 97, 145, 324, 389, 418, 427, 454, 462 all say MUST/BEFORE/AFTER).

*Fix (medium):* Turn daemon.ts into a pure module: export startDaemon(opts) that constructs subsystems in an explicit array of {name,start,stop} in one function body; keep only the cli.ts/import.meta.main call at module scope. This also makes cleanup() derive from the same list (see lifecycle finding).

#### R007 · P2 · gap · `lib/daemon.ts:85`
**Boot failures before stderr redirection leave no diagnostics anywhere**

If ~/.mattstack/rt/logs cannot be created or written (the directory or state.db is root-owned after a `sudo rt ...` invocation, which repo-index.ts:171 already names as a real case; disk full; a synced home dir with wrong ownership), getDaemonLogger() rejects at module scope, the process exits 1, and launchd respawns it every 10 s. Because fd 2 is only redirected inside startDaemon and the prod plist sets no StandardErrorPath, the exception text goes to /dev/null; `rt daemon logs` shows nothing, `launchctl print` shows only 'last exit code = 1', and the setup row says 'installed but not responding ... approve in Login Items', which is the wrong remedy. The dev shim already redirects fd 2 before any precondition for exactly this reason.

*Fix (trivial):* Call redirectNativeStderr() as the first statement of lib/daemon.ts (it only needs logsDir()), and/or add StandardErrorPath to the prod plist; have `rt daemon status` surface launchd's last exit code and the daemon-stderr.log tail.

#### R008 · P2 · gap · `lib/daemon.ts:329`
**No request id or caller identity across CLI/clients -> daemon; rejected commands are unattributable and unreproducible**

Six clients (rt CLI, tray, mr-board, gitq, console, chat viewer, shepherdr panes) share rt.sock. The log shows 'command rejected worktree:claim error=no such tree' 40 times in an hour with no payload (which repo? which tree?) and no caller. The user's cli..log shows their own `rt worktree claim` succeeded. There is no way to tie a daemon line to the invocation that caused it, so the report becomes 'sometimes it says no such tree'.

*Fix (medium):* Generate a short reqId per socket/REST request; put it in the response envelope and in every handleCommand log line; clients send `X-RT-Client: /` (rt-client transport + daemon-client.ts) and the daemon logs it; on rejected/failed, log a redacted payload digest (top-level keys plus repo/branch/iid/room when present). cli-logger records the reqIds a command issued.

#### R009 · P2 · rot · `lib/daemon.ts:374`
**No lifecycle seam: every subsystem hand-wires construction, cleanup and opts in three places, and half have no stop**

The next subsystem (say a notifications digest) must be added to daemon.ts construction, to buildRoutedHandlers opts, to cleanup(), and possibly to emit(); forgetting the cleanup line is invisible because process.exit follows. Tests cannot start/stop the daemon graph in-process because half the subsystems cannot be stopped, which is why daemon.ts wiring has no unit test at all.

*Fix (medium):* Introduce `interface Subsystem { name; start(ctx): Promise|void; stop(): void }`, register each in an array in startDaemon, run start in order and stop in reverse; pollers, reconciler and the sweep timers become subsystems with handles.

#### R010 · P2 · gap · `lib/daemon/handlers/chat.ts:183`
**chat:post validates neither room, handle nor body: typo'd rooms are a silent black hole and bad shapes 500**

(a) An agent posts to `deck` instead of `deck-main`. postMessage (lib/state/chat-store.ts:465-473) runs REVIVE (no-op), INSERTs the message into a room with no chat_rooms row and no members, recipientsFor returns [], and the verb answers `{ok: true, recipients: []}`. Nobody is woken, `rt chat rooms` never lists it, the message is unreachable except via chat:messages with the exact name. The CLI (commands/chat.ts:728) checks only the name pattern. (b) body missing or non-string: mergeMentions -> parseMentions -> `body.matchAll` TypeError escapes the handler, handleCommand logs at ERROR 'command failed' and the client sees a 500 with a TypeError string. (c) room containing `/` or `*` emits a reshaped `chat//msg` topic; handle is stored unvalidated. (d) `mentions` as a string instead of array TypeErrors the same way. chat:dm has the same shape: a DM to an unknown handle creates a dm room and returns ok (lib/state/dm-store.ts:61-71).

*Fix (small):* At the top of chat:post/chat:dm: isValidChatName(room) and isValidChatName(handle); `typeof body === 'string' && body.length > 0` (and a generous max, e.g. 64KB); `Array.isArray(mentions)`. Refuse a post to a room with no chat_rooms row (`roomArchivedAt(room) === undefined`) with an error naming the closest existing rooms, so a typo fails loudly instead of returning ok with no recipients.

**/api/status and tray:status have no degraded level; a daemon whose refreshes all fail still reports green**

#### R014 · P2 · rot · `lib/daemon/worktree-reconciler.ts:1062`

#### R015 · P2 · rot · `lib/state/db.ts:436`
**Idempotent column adds are gated behind user_version, so a cross-lane SCHEMA_VERSION collision has no self-heal**

#### R023 · P3 · gap · `lib/daemon.ts:456`

## Appendix C ... Claims investigated and refuted

Listed so a future audit does not re-raise them.

- `lib/daemon/api-server.ts:103` ... Port 9401 is a hard constant; EADDRINUSE at boot is an uncaught exception under launchd KeepAlive, giving a silent respawn loop
  - Refuted: The finding's central mechanism (EADDRINUSE at boot -> uncaughtException -> process.exit(1) -> silent 10s launchd respawn loop -> flapping rt.sock) does NOT occur on the prod path the finding explicitly targets ("users who are not the author"). Prod's launchd daemon is the compiled binary launched as `Contents/MacOS/rt --daemon` (LaunchAgent.plist:12-16), which enters via cli.ts:87-92 INSIDE async `__main()`, after `await import("./lib/daemon.ts")` at cli.ts:91. `startDaemon()` (daemon.ts:385, synchronous) throws when `startApiServer` calls `Bun.serve({port:9401})` (api-server.ts:103-104) with no try/catch (daemon.ts:469). Because that sync throw happens in the async continuation of an async function, it rejects `__main()`'s promise rather than propagating as a synchronous top-level exception; the call site `__main().catch((err)=>{throw err})` (cli.ts:58) re-throws inside a `.catch` callback, producing an UNHANDLED REJECTED PROMISE, which routes to the `unhandledRejection` handler installed at daemon.ts:392 (installCrashHandlers). That handler (daemon-logger.ts:242-244) logs at `error` and does NOT call process.exit. It never reaches the `uncaughtException` handler (daemon-logger.ts:237-240) that the finding relies on. With no exit, the socket server already bound at daemon.ts:468 keeps the event loop alive, so the process stays up as a degraded half-daemon (unix rt.sock serving CLI, REST/WS on 9401 absent). Therefore: no exit(1), no KeepAlive respawn loop, no rt.sock flapping. The finding's described failure is refuted for prod. The exact mechanism DOES hold for the DEV flavor only, whose shim execs `bun run /lib/daemon.ts --daemon` (Sources-daemon-shim/main.swift:269), making lib/daemon.ts the entry so `import.meta.main` is true (daemon.ts:517) and startDaemon() runs synchronously at top-level -> sync EADDRINUSE IS an uncaughtException -> exit(1) -> dev-plist respawn loop. But dev is the author's own machine, outside the finding's stated scope. The TRUE parts (hardcoded 9401 at daemon-config.ts:72, plist never passes RT_API_PORT so the env knob is dead under launchd, no port probe/fallback anywhere, Bun.serve throws EADDRINUSE synchronously) describe a real but different and milder defect: silent degradation, not a respawn loop.

- `lib/daemon/handlers/cache.ts:44` ... Unauthenticated GET /api/cache?maxAgeMs=0 forces a full multi-repo refresh from any web page
  - Refuted: Re-derived by the lead reviewer: GET /api/cache builds its payload from URL query params, so maxAgeMs arrives as the STRING "0"; the cache:read handler's numeric type check rejects it and no refresh is forced (the same coercion gap S085 documents). The route is therefore a stale-read, not a forced multi-repo refresh; the exposure that remains is the unauthenticated read itself, covered by S006/Phase 3.

- `lib/home/snapshot-owners.ts:69` ... Zone names containing pathspec magic characters break every auto-commit with add-failed
  - Refuted: Traced the full path: commands/home.ts:1071-1099 (`homeClaim`) takes a free-form CLI positional straight into `claimZone` -> `normalizeZone` (lib/home/snapshot-owners.ts:69-75), which only rejects empty/leading-"/"/backslash/"."/".." segments ... no check for pathspec magic or glob chars, so `rt home claim ':scratch'` is indeed accepted and stored as `:scratch/`. lib/daemon/home-snapshot.ts:657 does build `:(exclude)${zone}` by raw string concatenation for both `git add` (line 658) and `git commit` (line 683), sourced from `plan.excludedZones` = `Object.keys(owners.zones)` (lib/daemon/home-snapshot-plan.ts:121,126) with zero further sanitization. So the mechanical setup in the finding is accurate.

But the claimed *consequence* ... git raising "Invalid pathspec magic" (exit 128) on `:(exclude):scratch/`, causing "add-failed" and "every snapshot cycle fails... auto-commits silently stop for the whole home repo" ... does not reproduce. I ran the exact commands against the real git binary (Apple Git 2.50.1, same as this environment) in scratch repos:
- `git add -A -- . ':(exclude):scratch/'` -> exit 0, correctly excludes only that path.
- Also tried `:(exclude):(bogus)x/`, `:(exclude):/foo/`, `:(exclude)?x/`, `:(exclude))x/`, `:(exclude)(x/`, `:(exclude)x,y/` -> all exit 0, no pathspec-magic error.
Git's pathspec grammar consumes the `:(magic-list)` parenthetical exactly once; everything after the closing paren is taken as a single literal/glob pattern and is never re-scanned for a second leading `:` magic signature. A colon (or any of these other characters) inside the *pattern* portion is therefore inert, not an error trigger.

There IS a real, but different and narrower, defect adjacent to this: normalizeZone doesn't reject glob metacharacters (`*`,`?`,`[`), so they ARE interpreted by git as wildcards. For a FILE-kind zone with a literal glob-shaped name (no trailing slash, e.g. a real file named "*.log"), `:(exclude)*.log` over-matches (confirmed: excluded both "notes.log" and "logs/x.log" in a scratch repo ... matches the finding's "excludes far more" half). But for the more common DIR-kind zone (trailing slash always appended by normalizeZone's default `kind: "dir"`), the same glob shape becomes a complete NO-OP: `:(exclude)*.log/` matched zero files in testing, meaning the "claimed" zone loses its protection and gets silently auto-committed by the daemon ... the opposite failure direction from what's claimed, and with no error, no add-failed, no lastCommitError anywhere (exit 0 throughout).

- `lib/doppler-config.ts:54` ... Doppler config writer uses a fixed .tmp path and read-modify-write with no lock
