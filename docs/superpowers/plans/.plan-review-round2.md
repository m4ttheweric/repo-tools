## New findings introduced by the revisions

- **N1 (Important): identity overrides are honored inconsistently across the endpoint consumer.** The #4 fix wires `rt.repoIdentityOverrides` into `deriveRepoIdentity` only, while Task 7 directs run.ts and buildInterceptRules to use bare `normalizeRemote` on the remotes they hold. A fork-pinned repo (unrecognized remote mapped by an override) therefore resolves its store repo-sections in the daemon handler paths but yields identity null at install time (buildInterceptRules) and in the post-match read (run.ts) — the two paths that actually feed interception. Fix is one line of design: extract a sync `identityFromRemote(remote)` = machine-store overrides (readStore, sync file I/O — daemon-safe) + `normalizeRemote`, used by all three remote→identity sites; deriveRepoIdentity composes it after the spawn.
- **N2 (Minor): "migrate repoHasWorktreeActivity to the resolver" needs its activity predicate pinned.** The registry default `{onDeck:0}` means a resolved `rt.worktrees` value is ALWAYS present, so "resolved value exists" would qualify every registered repo and the gate stops gating. Define activity = registry entries > 0 OR rt.worktrees provenance includes any scope stronger than `default` (legacy or store), and make the dedicated test assert the negative case (fully unconfigured repo still skipped).
- **N3 (Minor): Task 2's SettingDef interface literal omits `pathGuardFields?: string[]`**, which the same task's registry contents and Task 5's refusal logic both rely on. Add it to the interface (and note the spec's SettingDef doesn't list it — a sanctioned implementation detail, like siblingCommand).
- **N4 (Minor): the per-test-HOME hygiene rule lives only inside Task 4's step text**, but Task 1's tests write fixtures at the real rt-paths store locations in the SHARED preload HOME (exactly the #7 leak shape) and Task 6's handler tests seed fixture stores with no repoint instruction. Hoist the rule to Global Constraints so T1/T5/T6 suites inherit it.
- **N5 (Nit): e2e staleness step** ("touch the team store → status reports stale") can flake when touch lands in the same mtime tick as install; set an explicitly future mtime (utimes) or compare with a margin.
