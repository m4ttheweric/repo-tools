# Plan review round 1 — rt settings resolver implementation plan (2026-08-20)

Reviewer: adversarial pre-execution pass against the approved spec (binding) and the live code in this worktree. Callsite claims verified by running the plan's own `rg` commands; jsonc-parser behavior verified empirically (spike in scratchpad, jsonc-parser latest).

## Critical

1. **Task 7's `loadEndpointRepoConfig` wrapper note is self-contradictory, unparseable text.** "remains as a thin wrapper that passes `repoIdentity: null` is WRONG — it must derive via memo when awaited callers exist; where a sync caller cannot await, it uses the legacy+global path" reads like an inline self-correction left in the plan; a fresh implementer cannot extract one behavior from it. Ground truth (verified): ALL four production callers are async — `lib/endpoint/run.ts:90` (inside async `runInterception`, with `rule.repoRemote` AND the freshly captured `remote` already in hand), `lib/endpoint/shim.ts:125` (inside async `buildInterceptRules`, which captures remotes itself), `lib/daemon/handlers/endpoint.ts:93,133` (async handlers with `ctx.repoIndex()` available). There is NO sync production caller; the "sync caller" clause is vestigial and sends the implementer down a phantom path. **Fix:** rewrite as one sentence — drop the wrapper (or make it async): run.ts calls `loadEndpointConfig({ repoIdentity: normalizeRemote(rule.repoRemote), repoName: rule.repo })`; shim.ts passes the remote it captures (normalized); daemon handlers `await deriveRepoIdentity(ctx.repoIndex()[repo])`; the only remaining sync callers are the unit tests, which Task 7 updates.

2. **Orchestrator steps run the migration against the OLD binary.** The listed order is: seed stores → remove migrated keys from live config.json → `rt intercept install` → daemon restart → smoke (`rt settings explain` …) → **merge to main LAST**. Until the merge/install, the live machine's rt (Homebrew binary or dev-mode pointing at the main checkout — explicitly declared "another session's territory") reads ONLY config.json: key removal kills roles/intercepts/worktrees live, old `rt intercept install` regenerates EMPTY rules, and `rt settings explain` doesn't exist in the old binary. "Branch green" in the worktree is not the spec's "resolver proves green end to end" on the live machine. **Fix:** reorder — merge → main + make the new build live (install / dev-mode swap, then daemon restart) + live smoke on the resolver FIRST; only then diff-then-remove the legacy keys, `rt intercept install`, and re-smoke.

3. **`repoHasWorktreeActivity` is a hidden worktree consumer no task migrates.** `lib/daemon/worktree-reconciler.ts:985-989` reads the raw `worktrees` key of config.json directly and gates the ENTIRE reconciler pass per repo (line 1020). It does not call `loadWorktreeRepoConfig`, so Task 8's `rg -n "loadWorktreeRepoConfig"` sweep misses it. After migration step 4 removes the legacy key, a repo whose worktree config lives only in the stores and whose registry is empty is permanently skipped — replenish never runs, which breaks exactly the "team invite fulfills rt settings from anywhere" bootstrap the spec's Problem section promises. **Fix:** add it to Task 8's file list — qualify via registry entries OR a resolver read (e.g. resolved `rt.worktrees` present / onDeck > 0), with a test.

## Important

4. **`rt.repoIdentityOverrides` is built but never wired.** Task 3 produces `applyIdentityOverrides` and Task 2 registers the key, but no task says any caller reads the machine store's overrides before/after normalization — as planned, the fork-pinning feature is dead code with a green test suite. **Fix:** state in Task 3 (or 7) that `deriveRepoIdentity` composes `getSetting("rt.repoIdentityOverrides")` + `applyIdentityOverrides` on the captured remote (note the T3→T4 dependency this creates, or wire it in T7 after the resolver exists).

5. **The spec's path-literal guard has no implementing task.** Spec ("Schema registry", last bullet): shared-scope validation rejects absolute-path-looking values, "enforced for wave-1 keys on the `hook` field specifically". Task 2's `validateValue` is type-only; Task 5's refusal list omits it. **Fix:** add to Task 5's `setSetting` refusals (validation needs the target scope, so it fits there better than T2) + one test: team-scope `rt.roles` with `hook: "/Users/..."` refused, machine-scope accepted.

6. **Team-store selection is unspecified.** `listTeams()` can return several teams; the spec defers multi-team *precedence* but the resolver must still decide which team store(s) to read, and neither document says. An implementer will invent it. **Fix:** one line in Task 4 — wave-1 behavior (e.g. overlay all teams in sorted order, or assert single team) with a two-team test.

7. **Shared-HOME test pollution will break Task 7's "keep existing tests green" promise.** `bun test` runs every file in one process over ONE preload temp HOME. User/team stores are GLOBAL state: fixtures Task 1/4/5 "write under the temp HOME" leak into every later test file that resolves settings. Concretely: `lib/endpoint/__tests__/config.test.ts` never re-points HOME (it relies on unique repo names in the shared HOME); once `loadEndpointRepoConfig` reads stores, a user-store fixture left by a settings test changes r1/r2/r3's resolution order-dependently. **Fix:** settings tests use a per-test `mkdtemp` HOME (the `lib/worktree/__tests__/config.test.ts` `beforeEach` pattern), and Task 7 adds the same `beforeEach` fresh HOME to endpoint config.test.ts.

8. **Task 5's header-comment write has a verified gotcha.** Spike result (jsonc-parser, this machine): `modify` on a file containing ONLY a header comment emits `{...} // header` — the header lands AFTER the closing brace. Creating the file as `// header\n{}\n` and then modifying keeps the header on line 1 (verified). Comment preservation for the plan's other edit shapes — nested identity-section creation with missing parents, sibling key insert next to a commented key, nested value overwrite — all verified working, so the byte-check test is achievable; note neighbors' VALUE formatting may be re-flowed even when comments survive (assert the comment line, not surrounding bytes). **Fix:** direct the implementer to seed absent stores as `// header\n{}\n` before `modify`, and make the header test assert the comment is the first line.

## Minor

9. **`setLegacyReader` ambiguity (Task 4):** the interface says "wired by consumers task" yet defines a default reader in T4 itself; with the default, consumers may never call the setter — dead global-mutable hook. Say whether any consumer actually calls it, or drop the setter and keep only the default. (Task 4's tests need NO stub: the default reader + a `repos/<name>/config.json` fixture suffices — worth stating.)
10. **Daemon `settings:get` expansion default unstated (Task 6):** default `expand:true` without ctx throws on `${repoRoot}` — a rejected API read by design accident. One line: daemon read handlers pass `expand:false`.
11. **Task 2 underspecifies `scopes` per def and the `rt.worktrees` default object** (`{onDeck:0, branchFormat:"<ticket>-<slug>", ready:[]}` per spec) — one line each avoids drift.
12. **`buildInterceptRules` ordering inversion unnamed (Task 7):** today it `continue`s on empty intercepts BEFORE capturing the remote (shim.ts:125-127); store-only intercepts require remote capture FIRST (spec: one spawn per registered repo). Name the inversion so the early-continue isn't preserved.
13. **Task 6 CLI verbs ship with no direct tests** (deferred to Task 9): refusal messages/flag errors are untested until the last task. Acceptable, but one unit test of the set-refusal path in commands/settings-keys.ts is cheap insurance.
14. **Task 9 hook-stub path nit:** `${team:e2eteam}` expands to `~/.mattstack/teams/e2eteam` (zone root), not `.../e2eteam/mattstack/` — place the stub relative to the zone root.

## Answers to the posed questions

1. **Task ordering/isolation:** sound. T1→T2→T3 independent; T4 needs only T1+T2 (identity is pre-derived by callers, no T3 dependency at resolve time); T5 needs T1+T2; T6 needs T4+T5+T3; T7 needs T3+T4 (+T6 for the set-regen test); T8 needs T4. Task 4's legacy hook needs no stub — the T4-defined default reader plus config.json fixtures carries its tests (#9 asks the plan to say so).
2. **Task 7 wrapper note:** not implementable as written — see Critical #1. The intended behavior IS implementable (every caller can await or already holds the remote); the text needs a rewrite, not the design.
3. **e2e seeding:** clean. `createTestHome()` is a fresh `mkdtemp` containing only `.gitconfig`/`.zshrc`; the seeded `~/.mattstack/teams/e2eteam/mattstack/settings.jsonc` matches `teamSettingsPath("e2eteam")` exactly, and `listTeams()` sees only e2eteam. No collision. (Nit #14 on the hook path.)
4. **Comment preservation:** verified empirically — yes for every edit shape the plan uses, with one trap (header-only files, #8). Discovery timing is fine since TDD puts the test first, but fold the seed-shape direction in now to save the debugging loop.
5. **Task 7 full-suite gate:** achievable. `lib/endpoint/__tests__/config.test.ts` traced: absent stores → `exists:false` no-op → legacy reader returns raw `roles`/`intercepts` → sanitizers produce byte-identical output — PROVIDED (a) sanitizers run post-resolution, (b) name→identity derivation degrades to null without repos.json instead of spawning/throwing (ties to #1), and (c) the shared-HOME pollution in #7 is handled. Without #7's fix the promise is order-dependent.
6. **Spec sweep:** unimplemented spec requirements found: overrides wiring (#4), path-literal guard (#5), plus the hidden consumer (#3). Team-store selection is a gap in BOTH documents (#6). Unsanctioned additions: only the `setLegacyReader` setter (#9) — harmless. Everything else maps: stores/format T1, registry+14 defs T2, identity T3, resolution/variables/teamLocked/skew labels T4, writes+refusals T5, CLI/daemon T6, endpoint+staleness three-parter T7 (set-regen, install, status/verify probe all present), worktree+proof case T8 (all five `loadWorktreeRepoConfig` callsites confirmed async: create.ts:59, worktree-reconciler.ts:745/878/979, handlers/worktree.ts:240 — plan's claim is TRUE, but the callsite list misses the non-caller consumer in #3), data migration correctly orchestrator-owned.
7. **Orchestrator sequencing:** unsafe as ordered — see Critical #2. Diff-then-remove itself is correctly diff-first; the binary-liveness ordering is the flaw.

The minors are implementer notes.
