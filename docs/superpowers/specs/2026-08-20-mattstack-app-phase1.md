# MAT-383 phase 1: rt-tray → mattstack.app (rebrand + dual-bundle dev mode + migration)

**Ticket:** MAT-383. **Date:** 2026-08-20, rev 5 (addresses reviews r1-r3 + the r4 inline review). **Recon basis:** scratchpad/tray-rebrand-ripple-map.md (all file refs verified there). **Rulings (Matt, 2026-08-20, recorded on the ticket):** clean-break bundle id `com.mattstack.app`; proper old-app migration in scope; on-disk name `mattstack.app` + one shared path constant; `com.rt.daemon` stays; dev mode = separate-dev-identity convention, no in-place binary swaps; homebrew retirement and the installer/updater (Sparkle, app-installs-rt) are **phase 2** — this spec keeps the existing release channel publishing the renamed app.

## Goal

After phase 1: the installed app is `~/Applications/mattstack.app` (`com.mattstack.app`, signed + notarized, display name "mattstack"); a dev build `mattstack-dev.app` (`com.mattstack.app.dev`) runs the daemon from source; `rt settings dev-mode on|off` switches which app is registered as the login item; every rt-tray reference in TS/CI is renamed through shared constants; upgrading an existing machine migrates cleanly off `rt-tray.app`.

## Design

### 1. Bundle identity (atomic group — one commit, per ripple map Group 1)

- `rt-tray/Info.plist`: `CFBundleIdentifier` = `com.mattstack.app`; `CFBundleExecutable`/`CFBundleName` = `mattstack`; `CFBundleDisplayName` = `mattstack`.
- `rt-tray/LaunchAgent.plist`: `AssociatedBundleIdentifiers` = `com.mattstack.app` (must match exactly or FDA inheritance to the daemon silently breaks). `Label` stays `com.rt.daemon` (ruling 4), as does the `Contents/MacOS/rt-daemon` program path. The codesign `-i rt-daemon` identifier override lives ONLY in the dev build's shim-signing step after this change (prod ships no shim, §3); it is load-bearing there and must survive.
- `rt-tray/build.sh`: TWO name variables, because they now diverge — `PRODUCT_NAME="rt-tray"` (the SwiftPM product; `.build/release/$PRODUCT_NAME` is where the compiled binary comes FROM — build.sh:26,30 derive the source path from the app name today, which breaks the moment they differ) and `APP_NAME="mattstack"` (the bundle: filename `mattstack.app`, `Contents/MacOS/$APP_NAME` copy destination). The currently-dead `BUNDLE_ID` variable gets wired into an Info.plist templating step (sed at build time) so the id lives in ONE place — build.sh — never two.
- `Package.swift` executable target keeps its `rt-tray` name (not user-visible; `PRODUCT_NAME` bridges it). Decision stated so nobody "fixes" it.
- Dev variant (same templating, different values): `BUNDLE_ID=com.mattstack.app.dev`, `APP_NAME`/display `mattstack-dev`, bundle `mattstack-dev.app`, installed at `~/Applications/mattstack-dev.app`.
- **Per-flavor daemon agent (r1 F2, completed per r2 finding 2):** `DaemonLifecycle.swift` registers `SMAppService.agent(plistName:)` and today hardcodes BOTH the plist name (`"com.rt.daemon.plist"`, line 17) and the kickstart label (`"com.rt.daemon"`, lines 49-50) as compiled Swift literals — templating the plist file alone re-points nothing. So: the daemon label becomes an Info.plist key **`MSDaemonLabel`** (templated by build.sh next to `BUNDLE_ID`: prod `com.rt.daemon`, dev `com.rt.daemon.dev`), and `DaemonLifecycle` reads it from `Bundle.main` for both `plistName` (`"\(label).plist"`) and every `launchctl` invocation. Prod ships `com.rt.daemon.plist` (Label `com.rt.daemon`, `AssociatedBundleIdentifiers` `com.mattstack.app`); the dev bundle ships `com.rt.daemon.dev.plist` (Label `com.rt.daemon.dev`, `AssociatedBundleIdentifiers` `com.mattstack.app.dev`) — one LaunchAgent.plist template, THREE values injected at build time: Label, `AssociatedBundleIdentifiers`, and `KeepAlive` (prod `true`; dev `{ SuccessfulExit: false }` — omitting this third one crash-loops the exit-0 dev launcher). TS side: **`currentMode()` MOVES from `commands/settings.ts:364` into lib** (new `lib/dev-mode.ts`, wrapper-presence logic unchanged; settings.ts imports it from there) so `lib/daemon-config.ts` can expose `activeLaunchdLabel()` = `currentMode() === "dev" ? "com.rt.daemon.dev" : "com.rt.daemon"` without a lib→commands inversion (settings.ts already imports daemon-config — the reverse import would cycle). `commands/verify.ts:229`'s `launchctl list` check uses it. **Active-flavor source of truth (r2 finding 3):** the existing `currentMode()` (`commands/settings.ts:364`, wrapper-presence based) remains the single source; dev-mode.json's schema (`{sourcePath, bunPath}`) does NOT change, and `disableDevMode()` leaving the file behind stays harmless because nothing derives flavor from the file's existence.

### 2. Shared constants (kills the 5-file literal sprawl, ripple map risk 4)

In `lib/rt-paths.ts` (the established single-source-of-truth module):

```ts
export const TRAY_APP_NAME = "mattstack";           // prod CFBundleExecutable — pkill/osascript use this
export const DEV_TRAY_APP_NAME = "mattstack-dev";   // dev CFBundleExecutable — the flavor-aware quit needs it
export const TRAY_APP_BUNDLE = "mattstack.app";
export const DEV_TRAY_APP_BUNDLE = "mattstack-dev.app";
export function trayAppPath(): string;               // ~/Applications/mattstack.app
export function devTrayAppPath(): string;            // ~/Applications/mattstack-dev.app
export function legacyTrayAppPaths(): string[];      // old rt-tray.app candidates, for migration + verify warnings
```

(`legacyTrayAppPaths` is a FUNCTION, not a const — `lib/rt-paths.ts`'s call-time-HOME rule, enforced by its source-guard tests, forbids baking HOME at module load.)

Consumers updated to the constants (no literals remain): `cli.ts:108`, `commands/verify.ts:135,147-153`, `commands/daemon.ts` (open/paths/user strings), `commands/settings.ts` (`RT_TRAY_APP` and the daemon-swap path family — see §3, most of that family is deleted; note daemon.ts/settings.ts also carry ~15 user-facing "rt-tray" strings the grep-gate forces), `commands/post-install.ts` (candidates, dest, osascript app name, `pkill -x`), `e2e/tests/verify.test.ts:70`, plus the two the earlier lists missed: `lib/notifier.ts` and `lib/daemon-config.ts` (both carry `rt-tray` literals — the grep-gate forces them regardless). Not generalized to `suiteAppPath(name)` — premature (ruling on ripple-map open question 5).

### 3. Dev mode: two bundles, zero surgery (the convention ruling)

- `build.sh dev` builds `mattstack-dev.app`: dev bundle id; menu-bar title rendered with a visible `dev` suffix; `UpdateChecker` disabled for dev builds (guarded by an Info.plist key `MSDevBuild=true` read at startup — one check, no compile-flag matrix). **Signing (r2 note): dev builds sign with the same Developer ID cert when it's in the keychain** (it is, on Matt's machine — `security find-identity` already drives prod builds) so the dev bundle's code identity is stable and its one-time notification/FDA grants stick across rebuilds; ad-hoc is the fallback only when no cert exists, with the stated caveat that grants may not survive rebuilds under it.
- The dev bundle's `Contents/MacOS/rt-daemon` is permanently the source-runner: today's `Sources-daemon-shim/main.swift` (reads `~/.mattstack/rt/dev-mode.json` for `sourcePath`/`bunPath`, execs bun) ships AS the dev app's daemon launcher, not as a swap payload. **Exit-code contract (r1 F4 + r2 note):** EVERY unconfigured/missing-precondition path in the launcher (all of today's `die()` sites: config missing, sourcePath gone, bun missing) exits 0 with one log line; only genuine crashes exit non-zero. The DEV plist sets `KeepAlive = { SuccessfulExit: false }` — clean exits stay down, real crashes still restart.
- **Socket mutual exclusion (r1 F3):** both flavors bind `~/.mattstack/rt/tray.sock`, and today's `TrayServer.swift:27-30` unlink-and-rebinds blindly (last-launched silently steals every `rt daemon *` command). New rule, both flavors: on startup, ping the existing socket first — **and this guard completes BEFORE `SMAppService` registration runs** (a manual double-launch must exit without registering, or both daemon agents end up registered and fight over rt.sock/rt.pid even after the losing tray exits); if a live tray answers, log "another tray owns the socket" and exit. The dev-mode toggle's quit-then-launch ordering makes this a belt-and-suspenders guard, not the primary mechanism.
- `rt settings dev-mode on|off` is rewritten as a **handoff, not just an app quit** (r2 finding 1: quitting a tray stops only its timers and TrayServer — `applicationWillTerminate`, `AppDelegate.swift:84-89` — while its launchd agent keeps running under `RunAtLoad`+`KeepAlive`; two registered flavors mean two daemons SIGTERM-ing each other over the shared `rt.pid`). Sequence for `on` (mirror for `off`): (0) **precondition — the incoming flavor's bundle exists on disk** (`devTrayAppPath()`/`trayAppPath()`); abort with a "run build.sh dev first" hint BEFORE touching the running flavor, so the toggle can never leave the machine tray-less; (1) `POST /flavor/retire` to the outgoing tray's TrayServer — a NEW endpoint that calls `service.unregister()` on its own daemon agent AND `SMAppService.mainApp.unregister()` on its own login item (this replaces the deleted `/login-item/reset` as TrayServer's registration surface); (2) quit the outgoing tray **by its own flavor's names** — `osascript tell application` with the outgoing display name, `pkill -x` with the outgoing CFBundleExecutable (`TRAY_APP_NAME` / `DEV_TRAY_APP_NAME`); (3) **poll until the outgoing pair is actually gone** — the socket check is a CONNECT-probe, not file existence (a pkill'd tray leaks the socket file), plus `launchctl list <outgoing label>` empty, bounded wait — required because the incoming tray's ping-then-exit guard (above) would otherwise see the dying socket and abort; (4) launch the incoming app. **Login-item reality (`SMAppService.mainApp` is a USER toggle today — `ProcessPanelView.swift:97-100` — it never auto-registers at startup):** the incoming app's AppDelegate gains idempotent startup registration — if `mainApp.status == .notRegistered`, register — so a flavor switch preserves start-at-login without a manual re-toggle; the panel toggle remains the user's opt-out and wins (an explicitly disabled login item is NOT re-enabled: record the opt-out in the app's own UserDefaults and skip auto-register when set). The daemon agent registers at startup exactly as today. Never mutates a bundle in place. The entire swap machinery in `commands/settings.ts` (`swapDaemonToShim`, `DAEMON_REAL_BACKUP`, `DAEMON_SHIM_PATH`, restore paths, the LWCR reset dance and its long comment) is DELETED — the tray-install-clobbers-dev-mode scar and the stale-LWCR EX_CONFIG class die structurally, because prod's bundle is never modified and each identity's registration is stable. **Deletion edges ruled (r1 F8):** the PROD bundle stops embedding and signing `rt-daemon-shim` entirely (the shim ships only as the dev bundle's `rt-daemon`, signed with the SAME identity as the rest of the dev bundle (bundle-wide identity — a nested ad-hoc binary inside a Developer-ID hardened-runtime bundle is an invalid signing config) keeping the `-i rt-daemon` identifier override; build.sh's prod path drops the shim steps entirely); `TrayServer`'s `/login-item/reset` endpoint is deleted with its only caller (the LWCR dance).
- **The CLI half of dev mode survives untouched (r1 F9):** `~/.local/bin/rt` source wrapper, the preload, shell integration, `IS_DEV_MODE`, and `UpdateChecker.isCliDevMode` all stay; `rt settings dev-mode` keeps toggling BOTH halves (CLI wrapper + app flavor) through the same dev-mode.json.
- Cost accepted (ruling): `com.mattstack.app.dev` gets its own one-time notification/FDA grants.

### 4. Migration from rt-tray.app (post-install, ripple map risks 2+5)

`rt --post-install` gains a one-shot legacy sweep — **post-install ONLY, explicitly NOT `rt daemon install`** (r1 F6: post-install spawns daemon install at `post-install.ts:141` AFTER the new app registers, so a sweep there would boot out the daemon it just started), and **GUARDED: the sweep runs only when `legacyTrayAppPaths()` finds an existing legacy bundle on disk** (r2 finding 4: `rt update` re-execs `--post-install` on every update — `update.ts:73-76` — and step 2's bootout targets `com.rt.daemon`, the label prod KEEPS, so an unguarded sweep would kill the live daemon on every routine update forever). Order when the guard fires, all before installing the new app:

1. Quit: `osascript -e 'tell application "rt-tray" to quit'` (old name), then `pkill -x rt-tray` fallback.
2. Stop the old job: `launchctl bootout gui/$UID/com.rt.daemon`. **Honest limitation (r1 F5):** bootout stops the job but does NOT remove the old bundle's BTM/SMAppService registration record — only the old app itself could unregister it, and it is about to be deleted. The inert record (a ghost row in System Settings → Login Items) persists until manually removed; sole-user cost accepted, no claim that macOS drops it. `rt verify` warns while a legacy bundle path still exists.
3. Remove: `rm -rf` each existing `legacyTrayAppPaths()` entry.
4. Install + launch `mattstack.app`; its own startup performs SMAppService registration exactly as today's code does. **Success detection:** post-install then pings the daemon socket/health endpoint and reports loudly if the new registration did not come up — migration must not end on an unverified "should work".
5. Print the one-time note: "notification + full-disk-access permissions must be re-granted (bundle id changed)".

New `CFBundleExecutable` tracking: the osascript/pkill strings for the NEW app use `TRAY_APP_NAME` — upgrade-quit keeps working on the next rename (risk 5).

### 5. verify + the standing vsix failure

- `commands/verify.ts` tray-check contract (r1 F10, one rule, no contradictions): hard-fail only when the ACTIVE flavor's app is missing (active = `devTrayAppPath()` when `currentMode() === "dev"`, else `trayAppPath()` — currentMode is the ONLY flavor signal, per §1; dev-mode.json's existence is explicitly not one); the inactive flavor's absence is informational; any `legacyTrayAppPaths()` hit is a warning ("old rt-tray.app still present"). The `launchctl list` check uses `activeLaunchdLabel()` (§1). `e2e/tests/verify.test.ts:70` updates to this contract.
- The rt-context.vsix check drops `brew --prefix` entirely (its live bug: printing a non-existent prefix on dev machines, red since v2.7.0) and becomes a **presence check, not a version check** (r2 finding 5: version-matching is underivable — the extension versions independently of the CLI — and `findVsix()` is module-private and shells `npm run package`; verify must never build). New check: the rt-context extension directory exists under at least one installed editor's extensions dir (`~/.vscode/extensions/`, Cursor's equivalent) → pass, naming which; none found but an editor is installed → warn; no editor present → skip. Pure directory reads, no subprocess. (Brew's full wind-down is phase 2; this just stops verify lying today.)

### 6. CI (`.github/workflows/release.yml`) — trailing group, after 1-5 prove out locally

- Rename every `rt-tray.app` path (`dist/{arch}`, the arm64→x64 copy, notarize/staple targets) to `mattstack.app`; DO NOT reorder the notarize steps — the x64 leg deliberately copies the already-stapled arm64 bundle (risk 8).
- Generated Formula: `prefix.install "mattstack.app"`; Formula name/class (`rt.rb`/`Rt`) and tap unchanged — the channel itself retires in phase 2, no point renaming a dying formula.
- `UpdateChecker` keeps pointing at `m4ttstack/rt` releases (settled brand-vs-org-slug ruling); its alert copy still says "run: rt update" (the CLI is still `rt`).

### 7. Icon + cosmetics (trailing)

- `make-icon.swift`: new "m" wordmark; **regenerate the iconset AND `AppIcon.icns` and COMMIT both** (both are git-tracked and CI builds from them — r1 F12; build.sh's regenerate-only-if-absent guard is exactly why the regen must happen at change time, not build time); dev icon gets a tinted variant.
- UI strings: menu-bar wordmark, "Quit mattstack", panel titles, update-alert title. Grep-audited, not sed-blasted (risk 9: the `-i rt-daemon` codesign override and every `com.rt.daemon`/`rt.sock`/`tray.sock`/log-surface string are correct as-is and MUST survive).

## Non-goals (phase 2+, separate spec after its own design pass)

Sparkle; the app installing/updating the rt binary; brew/formula/tap wind-down; `rt update` rewrite; the onboarding wizard and installer flow; `com.rt.daemon` rename (never); org/tap naming reconciliation (MAT-30/MAT-376); tray log surface name (`tray.*` stays — auto-discovery contract).

## Verification

Automated: unit tests for the new rt-paths helpers (`trayAppPath`/`devTrayAppPath`/`legacyTrayAppPaths`, call-time HOME); e2e verify test updated to the active-flavor contract in §5; sweep-guard test: post-install with NO legacy bundle on disk performs zero quit/bootout/rm calls (the every-rt-update regression); dev-mode toggle test with PATH-faked `launchctl` + a fake tray socket asserting the handoff order (precondition-check → retire → quit → wait-until-gone → launch) and that a missing incoming bundle aborts BEFORE any retire/quit call; the migration sweep tested via the codebase's existing PATH-fake convention — a temp-HOME run with faked `osascript`/`pkill`/`launchctl` binaries recording invocations, asserting quit→bootout→rm all happen before install (no dep-injection seam exists in `post-install.ts` today; the PATH fake needs none); a unit test of the vsix PRESENCE check (§5): fixture extensions dirs → extension present in one editor = pass naming it; editor dir present but extension absent = warn; no editor dirs = skip — no subprocess, no findVsix. Grep-gate, scoped honestly (r1 F13): zero `rt-tray` literals in **TypeScript sources** outside `legacyTrayAppPaths()` — the `rt-tray/` directory name, the SwiftPM target/product name, TrayLog surface strings, git history, and docs are exempt by design.

Manual smoke (on Matt's machine, the only install base): `build.sh dev` → dev app runs daemon from source, menu bar shows dev mark, update check silent; `rt settings dev-mode on` then `off` round-trips registration; `build.sh release` + install → migration sweep removes rt-tray.app, prod app launches, notifications re-granted once, `rt verify` green including the vsix check.
