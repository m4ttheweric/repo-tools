## Scrutiny of the new machinery

### Wave-1 worktree walk (deep merge), field by field

Scopes: default `{onDeck:0, branchFormat:"<ticket>-<slug>", ready:[]}` (root reader-computed, namePool absent); legacy `{namePool, onDeck, root, branchFormat, ready}`; team.repos `{onDeck, ready}`; user.repos `{namePool}`. Walk weakest→strongest (default → legacy → team.repos → user.repos):

- **onDeck**: 0 → legacy → **team** wins.
- **ready**: [] → legacy array → **team** array wins (arrays replace atomically — correct; no rule splicing).
- **namePool**: legacy → **user** wins. "My namePool wins" holds. ✓
- **root**: **legacy** survives (no store carries it) — correct during the window; falls to the reader's computed default when step 4 removes the legacy key.
- **branchFormat**: **legacy** survives → falls to registry default at removal.

The semantics produce exactly the intended per-field coexistence, and the result matches user expectation. Two migration-content consequences (checked against the REAL assured-dev config.json, which has `onDeck:3`, a 32-name pool, and a 2-step ready incl. `pnpm genTypes`, and NO root/branchFormat):

- The moment the team store lands, team's `onDeck`/`ready` shadow the user's own legacy values (legacy < team by design). The seed must copy the live values (`onDeck:3`, both ready steps) or behavior silently changes *before* step 4. Wave-1 is safe if the orchestrator seeds from the live file — say so.
- Step 4's key removal silently drops any legacy-only field never seeded into a store (root/branchFormat in the hypothetical; empty set in the real file). Add one line to step 4: diff legacy vs merged-minus-legacy (or run `explain`) and port legacy-only fields before deleting. (NEW-1, should.)

### Closed-set variable expansion

No remaining collision: closed-set names (`repoRoot`, `worktree`, `home`, `team:*`) are disjoint from every domain template in the real config (`${port}`, `${roles.<name>.port}` in env, `${envKeys}` in argInject). "Replaces ONLY the closed set; any other `${...}` passes through verbatim" is a per-occurrence rule, which is per-string partial expansion — implementable as one regex pass over `\$\{[^}]*\}`. `${team:claimview}` in the hook expands while `${port}` in the same object passes through. Specified clearly enough. Two nits: no escape syntax for a literal closed-set token (fine to declare unsupported); and a `${worktree}`/`${repoRoot}` inside a value read in a context lacking that ctx (e.g. `buildInterceptRules` at install time has no worktree) hard-errors by design — acceptable loudness, but the daemon's read-only `settings:get` should state its expansion default (expand:false or explicit ctx) so an API read can't throw on `${repoRoot}` (NEW-6, nit).

### migrated:false refusal vs. the legacy-writing subcommands

`rt settings notifications`/`runaway`/`llm` write the legacy files while `rt settings set rt.notifications ...` refuses — same family, two doors. Not a conflict: the refusal is honest (the store value would be dead) and the spec explicitly leaves those subcommands unchanged. UX fix is one line: the refusal should point at the live sibling subcommand where one exists (`use: rt settings notifications`), not just the legacy file path (NEW-4, nit).

### Provenance for deep-merged keys

Under-specified. The signature says `{ value: T; provenance: Provenance }` (one object) while the trailing comment says "deep keys: provenance = per-contributing-scope list" — the type and the comment contradict, and `listSettings` rows inherit the ambiguity. Prescribe the shape: `provenance: Provenance[]` always (contributing scopes weakest→strongest, single element for replace keys), with per-field value attribution recoverable via `explain` (which already returns per-scope present/value). One-line type fix; intent is unambiguous, so should, not must. (NEW-2.)

### Daemon-thread safety

Holds. The handlers are async and can await the memoized `deriveRepoIdentity`; the spawn is `runCapture` (async Bun.spawn), never sync-exec (MAT-222 class avoided); the resolver itself is sync-file-I/O only. Two footnotes: memoize the *promise* so concurrent first claims don't double-spawn; and the spec's identity-derivation section enumerates only the endpoint callers — `loadWorktreeRepoConfig` has 5 non-test callsites (worktree/create.ts, worktree-reconciler.ts ×3, handlers/worktree.ts), all with repoPath in hand and all in async contexts, but its sync signature must grow a `repoIdentity` param (or the callers await the helper first); say so explicitly (NEW-7, should). Also, `buildInterceptRules` today spawns git only for repos WITH intercepts; needing identity to look up store sections makes it one spawn per registered repo (~20). Install-time only, fine — but the "zero extra spawns" claim is slightly overstated (nit).

### Version-skew: registered key, newer value shape

Gap. Unregistered keys warn+skip, but a REGISTERED key whose file value fails the def's `type` (or a non-object contribution to a `merge:"deep"` key) has no specified behavior — a hard error there re-opens exactly the brick class #6 closed. Specify: a scope contribution that fails the def's type check is warned, skipped (that scope only), and labeled in `list`/`explain`, same as unregistered. (NEW-3, should.)

## New findings (none are musts)

1. **(should)** Migration step 4: port legacy-only fields (and seed team values from the live file) before removing legacy keys — deep merge makes removal a behavior change for any field no store carries.
2. **(should)** Fix the `getSetting`/`listSettings` provenance type: `Provenance[]`, weakest→strongest, length 1 for replace keys.
3. **(should)** Specify type-mismatch handling for registered keys in store files: warn + skip that scope's contribution, labeled — never a hard resolution failure.
4. **(nit)** `set` refusal on migrated:false keys should name the live subcommand (`rt settings notifications` etc.) where one exists, not only the legacy file.
5. **(should)** Register `rt.repoIdentityOverrides` itself (machine-only, replace, migrated:true) — as written it appears in neither list and would be labeled `unregistered` by its own resolver.
6. **(nit)** State the daemon `settings:get` expansion default (expand:false or caller-supplied ctx) so an API read can't throw on `${repoRoot}`.
7. **(should)** Extend the identity-plumbing enumeration to the worktree consumer: `loadWorktreeRepoConfig`'s 5 callsites and how each obtains `repoIdentity`.
8. **(nit)** Staleness probe covers store mtimes only; a hand-edit to legacy config.json during the window still stales intercepts.json silently — no worse than today, worth one sentence.

## Verdict

**APPROVE.** All three round-1 musts (#1, #2, #3) are genuinely fixed — the merge semantics reproduce the wave-1 case correctly against the real config, the expansion contract exempts the domain templates that exist in the wild, and the name/identity bridge reaches the legacy file. The remaining items are one-line prose fixes an implementer can fold in without another design round; none changes the architecture. Fold NEW-1/2/3/5/7 into the spec before task breakdown.
