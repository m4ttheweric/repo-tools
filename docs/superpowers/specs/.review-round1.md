# Review round 1 — rt settings resolver design (2026-08-20)

Reviewer: adversarial pre-implementation pass. Non-negotiables not relitigated.

## Critical

1. **Object merge semantics are unspecified and the spec's own proof case contradicts the implied default.** "Most specific wins" reads as atomic per-key replacement, but the wave-1 worktree migration ("namePool lands in the USER store, team may carry onDeck/ready defaults") only works with deep merge — an atomic user `rt.worktrees: {namePool}` would shadow team's onDeck/ready entirely. Same question for `stores > legacy > default`: today's `loadWorktreeRepoConfig` applies per-FIELD defaults (onDeck ?? 0, root ?? computed), i.e. field-level merge with defaults; atomic store-over-legacy would drop a legacy onDeck the moment any store carries the key. **Fix:** add a per-key merge policy to `SettingDef` (e.g. `merge: "deep" | "replace"`, arrays always replace), state exactly how legacy and default participate in the merge chain, and re-verify the namePool/onDeck example against it.

2. **`${...}` expansion collides with domain templates — the spec's own example value breaks its own rule.** The seeded `rt.roles` value embeds `"env": { "PORT": "${port}" }` (an interceptor RUNTIME template, cf. `lib/endpoint/config.ts` RoleConfig.env `${port}`, `${roles.<name>.port}`), yet the spec says "unexpandable variables error loudly" and `expand: true` is the default. Reading `rt.roles` as designed errors on `${port}`. **Fix:** define expansion over the closed variable set only (`${repoRoot}`, `${worktree}`, `${home}`, `${team:*}`); every other `${...}` passes through verbatim. While there: state whether `${team:X}` expansion is purely lexical or existence-checked (Q4 — the spec is silent; lexical is right, the hook is already fail-open at exec time).

3. **The legacy fallback is unreachable from the new signature.** `loadEndpointConfig(identity)` must fall back to `~/.mattstack/rt/repos/<repoName>/config.json`, but that path needs a repo NAME and repos.json maps **name→path** (verified live: `"assured-dev": "/Users/matt/Documents/GitHub/assured/hogwarts"`). Identity→name requires a reverse walk of repos.json with a git spawn per candidate. The out-of-scope line "repos.json … stays the identity→path registry it is" mislabels the file and hides this gap. **Fix:** carry repoName (or repoPath) alongside identity through the fallback window (`loadEndpointConfig(identity, { legacyRepoName? })`), and correct the repos.json wording.

## Important

4. **`Provenance` has no `legacy` scope.** The enum is `"machine.repo"|…|"default"`, but legacy is a real value source between stores and default. `explain`/`get` cannot honestly report a legacy-served value — contradicting both the honesty invariant and the "migration progress is observable" claim. **Fix:** add `"legacy"` (with the config.json file path) to the Provenance union.

5. **teamLocked ordering is ambiguous.** Precedence puts `machine.repos` on top; teamLocked says "team value wins over user/machine". Does `team.repos` beat `machine.repos` for a locked key? Does a locked team GLOBAL value beat a team.repos value? **Fix:** state the exact locked-key ordering (suggest: `team.repos > team > default`, everything else shadowed and marked in `explain`).

6. **Unknown keys found IN store files = version-skew brick.** "Unknown key on READ = error" is stated for the key argument, but the spec never says what happens when a *store file* contains a key this binary's registry doesn't know. Teammates run Homebrew-distributed binaries at different versions; one new key pushed to the team store must not brick every older rt (`listSettings`, or any resolution pass that validates files). **Fix:** unknown keys *in files* are warn/labeled-unknown; hard error only for explicit `get`/`set` of an unregistered key.

7. **Entries-only registry surfaces make `list` and `set` lie.** For the 14 unmigrated keys, `rt settings list` shows registry defaults (provenance "default") while the live reader uses `~/.mattstack/rt/llm.json` etc. — the shown value/provenance is wrong whenever the legacy file diverges. Worse: `rt settings set rt.llm …` validates, writes the store, and *silently does nothing* — exactly the dishonesty class the design bans. **Fix:** add `migrated: boolean` (or `readsFrom: "legacy:<path>"`) to `SettingDef`; `list` labels unmigrated keys ("reader not migrated — value not authoritative"); `set` refuses (or loudly warns on) unmigrated keys. Acceptable-with-labeling, trap without.

8. **intercepts.json staleness story is incomplete.** Regen fires only on `rt settings set`, but the whole point of repo-backed JSONC stores is hand-editing and `git pull` in the team/user zones — neither triggers regen, recreating the staleness bug class the Problem section indicts. **Fix:** keep `rt intercept install` as the manual regen, add a staleness probe (store-file mtimes vs cache mtime) to `rt intercept status`/`rt verify`, and add an explicit "regenerate intercepts.json + reinstall shims" step to the migration checklist (it's missing there too).

9. **Sync `getSetting({ cwd })` implies sync git spawns — including on the daemon thread.** `deriveRepoIdentity(cwd)` needs toplevel + remote; the daemon endpoint handlers (`lib/daemon/handlers/endpoint.ts:93,133`) will need identity after migration, and a sync spawn on the daemon thread is the known MAT-222 wedge (Bun sync-exec). **Fix:** make `deriveRepoIdentity` async (or a pure-file .git/config parse, no spawn); `getSetting` stays sync but takes only `repoIdentity` — callers derive it from data they already have: `rule.repoRemote` in `lib/endpoint/run.ts:90`, the already-captured remote in `buildInterceptRules` (zero additional spawns; install-time cost unchanged at one spawn per repo, and the 3-file parse × ~30 repos is fine — optionally allow a memoized snapshot for batch callers).

10. **`repoIdentityOverrides` keyed by toplevel path breaks under worktree pools.** Six assured worktrees = six distinct toplevels; a fork override must be repeated per slot and re-added for every new ephemeral tree. **Fix:** key overrides by normalized remote URL → identity (covers all worktrees of the clone at once), or allow path-prefix matching.

## Minor

11. **`rt.worktrees.root`:** its default is computed (`join(repoPath, ".worktrees")`) — a registry `default` can't express that (keep it in the reader; say so), and a root value in a shared scope is a path literal smuggled inside an object that type-level validation can't see. Document that root must use `${repoRoot}`/`${home}` in shared scopes.
12. **Two JSONC parsers after this lands:** `lib/jsonc.ts` (stripJsonc) and jsonc-parser. State that resolver reads use jsonc-parser's parse too (one library for the settings subsystem), or explicitly bless the split.
13. **Store paths live outside `rtDir()`** (`~/.mattstack/user`, `~/.mattstack/teams`, `~/.mattstack/settings.local.jsonc`) while `lib/rt-paths.ts` is the source-guarded single home for layout. Name where the store-path constructors live (rt-paths.ts extension or `lib/settings/paths.ts`) and whether the source guard extends to them.
14. **Team-scope `setSetting` writes an uncommitted file in a git zone.** One line needed: the write is local; commit/push is the team-zone tooling's job, teammates don't see it until then.
15. **Local-path remotes produce path-shaped identities.** repos.json really contains `"origin": "/private/tmp/rt-escalation-demo/work"` — normalization of a filesystem-path remote yields a "path identity" in violation of the identity-never-path rule. Normalize only recognized host forms (ssh/https/scp-like); everything else → identity null.
16. **Migration checklist gaps beyond #8:** update the multi-owner doc headers in `lib/endpoint/config.ts` and `lib/worktree/config.ts` (ownership of config.json keys changes); state explicitly that `loadWorktreeAppConfig` (enabled/killProcesses, worktrees.json + parking-lot seed) stays legacy in wave 1; daemon restart required to pick up migrated handlers.

## Answers to the posed questions

1. **Internally consistent?** The precedence list, teamLocked, and legacy-fallback statements each hold alone but collide at the edges: teamLocked vs machine.repos is undefined (#5), Provenance omits legacy (#4), and `stores > legacy > default` is NOT implementable for object keys without a merge rule — the spec's own namePool/onDeck example requires deep merge while the precedence prose implies replacement (#1). Yes, it's a gap, and the biggest one.
2. **Identity from worktrees:** verified empirically — all six assured worktrees return `https://gitlab.com/assured/assured-dev.git` from `git config --get remote.origin.url` (worktrees share the common config). A pruned/broken worktree fails the git call → identity null → honest global-only degrade, acceptable. Teams-zone clones carry their own origin, fine. The real failure modes are local-path remotes (#15) and per-toplevel overrides under pools (#10).
3. **Hot loops:** `rt intercept run`'s match path stays on the intercepts.json cache (unchanged); the post-match config read (`run.ts:90`) and daemon endpoint handlers are the paths to watch — derive identity from `rule.repoRemote`/known remotes, never a fresh spawn, and never a sync spawn on the daemon thread (#9). `buildInterceptRules` at install time: one spawn per repo already exists; reuse it for identity; 3-file re-parse per repo is acceptable but memoizable.
4. **`${team:claimview}` for a solo user:** the spec does not say. In practice the value rides in the team store, so no team → value unreachable; but the expansion contract (lexical vs existence-checked) must be stated, and the same contract must exempt `${port}`-class domain templates (#2).
5. **setSetting nested addressing:** yes — jsonc-parser's `modify` takes a JSONPath segment array; `["repos", "<identity>", "rt.roles"]` addresses nested sections (dots/slashes inside a segment are fine) and creates missing parents. The `{ repoIdentity? }` opt suffices. jsonc-parser confirmed absent from package.json — genuinely one new dependency.
6. **Migration steps:** key removal IS specified ("REMOVED after the resolver proves green"), and a stale legacy roles key is harmless while the store carries the key (stores win) — but under deep-merge semantics a stale legacy field could keep applying invisibly (folds into #1). Load-bearing omissions: intercepts.json regen/reinstall step (#8) and doc-header/ownership updates (#16).
7. **Entries-only registry:** as specced it lies (#7). Acceptable only with an explicit unmigrated label on `list` and a refusal (or loud warning) on `set`.
8. **Convention conflicts:** store paths vs the rt-paths source guard (#13); duplicated JSONC primitive (#12); the three-owners-one-file headers must be rewritten as part of the migration (#16); module-registry/docs:gen/no-outcome-logging are correctly covered by the spec's invariants.

## Verdict

**REVISE.** Must change before implementation: #1 (merge semantics — blocks the wave-1 worktree case outright), #2 (expansion contract — the seed value errors as written), #3 (legacy fallback needs a name/path bridge). Should be decided in the same pass, cheap to fix in prose: #4, #5, #6, #7, #8, #9. The minors can land as spec footnotes or implementation notes.
